## 1.2 Problem Statement (replace entire section)

> Alumni and professional networks should connect every trainee with the mentor whose competencies best fit their development needs, and should preserve the knowledge exchanged so that later cohorts can reuse it. In practice, organisations still manage these relationships through email, WhatsApp groups and spreadsheets, which produce dispersed information, outdated records and declining participation (CASE, 2022). The platforms that exist, such as Graduway, Hivebrite and Chronus, connect people through keywords, tags or administrator-defined attributes (Table 2.1). A mentor who describes their expertise as "Machine Learning Engineer" and a mentee who searches for "Data Scientist" are therefore treated as unrelated. **[Add one quantified statistic with citation, e.g. alumni participation rates or keyword-search miss rate.]** Knowledge shared in chat threads is also unindexed, so it cannot be retrieved later, and once a mentorship starts there is no shared place to record sessions, goals and follow-up actions.
>
> As a result, suitable mentorships go undiscovered, running mentorships are hard to sustain, and institutional knowledge decays. This study therefore develops Alumni Connect, a platform that uses Sentence-BERT embeddings and cosine similarity for competency-based mentor-mentee recommendation and supports the mentorship lifecycle after matching. It evaluates the matching against a keyword baseline using precision, recall and mean reciprocal rank.

## 1.5 Justification (replace entire section)

> Prior work shows that Sentence-BERT embeddings outperform keyword methods on semantic similarity and recommendation tasks (Reimers & Gurevych, 2019a; Colangelo & others, 2025), and that BM25 remains a strong lexical baseline (Thakur et al., 2021). Commercial alumni and mentoring platforms provide strong institutional integration and programme administration (Graduway, 2024; Hivebrite, 2024; Chronus, 2024). However, none applies embedding-based matching, none is designed for sparse and acronym-heavy alumni profiles, and none retains the knowledge exchanged in mentoring (Section 2.5). Consequently, trainees miss relevant mentors and organisations lose longitudinal career knowledge. Alumni Connect addresses this with semantic matching and a mentorship workspace that keeps sessions, notes, goals and outcomes in one place. It is expected to surface relevant mentors that keyword search misses, which this study measures against a baseline. It benefits administrators by reducing manual coordination, helps alumni and trainees find relevant mentors, and adds evidence on transformer embeddings for short, specialised profile text.

## 1.6 Scope (replace entire section)

> **Technical scope.** A web-based client-server platform: a FastAPI backend, a React frontend, a relational database and a Sentence-BERT matching engine with a ChromaDB vector store. The backend is a single modular service rather than a set of microservices.
> **Data scope.** Synthesised member profiles, career paths and mentorship records modelled on technical training and corporate apprentice trajectories for 2020 to 2026.
> **Functional scope.** Role-based registration and login (email verification and one-time code), career profiles, mentor recommendations with a short explanation, mentorship requests, availability and booking, messaging, a mentorship workspace (sessions, notes, goals, action items, progress, closure and feedback), connections, notifications, career resources and administration.
> **Time scope.** Implementation from August to November 2026.
> **Exclusions.** Real-time audio or video, native mobile applications, non-English profiles, live LinkedIn or WhatsApp integration, retrieval-augmented answers over mentorship conversations or member data (the library feature uses only administrator-published text) and verification against an official staff or student register.

## Chapter 3

### 3.1 Introduction (replace)

> This chapter presents the methodological approach. The study follows an experimental research paradigm for the semantic matching engine (Section 3.2) and a hybrid system development methodology (Sections 3.3 and 3.4): Design Thinking is used to understand users and shape the solution, and Agile Scrum is used to build and deliver it iteratively. Analysis and design follow Object-Oriented Analysis and Design (OOAD), because the system is organised around users and related entities such as profiles, mentorships, sessions and conversations (Section 3.5). Section 3.6 lists the tools and Section 3.7 the system modules.

### 3.2.3 Model Selection and Configuration (append)

> A pre-trained Sentence-BERT model (`all-MiniLM-L6-v2`) and a version fine-tuned on domain profile text are compared; no model is trained from scratch because the dataset is small. Embeddings are normalised so cosine similarity reduces to a dot product.

### 3.2.4 Model Validation and Testing (append)

> Matching is evaluated on 21 synthetic mentee queries against 14 mentors using P@1, P@3, Recall@3 and MRR, against random and TF-IDF baselines (Chapter 5). Because recommendations are advisory, a human remains in the loop: the system ranks mentors, the mentee decides whether to send a request, and the mentor decides whether to accept it. Evaluation uses a fixed random seed for reproducibility. Because no model is trained on the query set, no held-out split is needed; if fine-tuning data is extended, a 20 per cent held-out set will be excluded from training.

### 3.3 System Development Methodology (replace opening and 3.3.1)

> Alumni Connect uses a hybrid of two methodologies with distinct roles. **Design Thinking** governs *what* is built: it keeps the design centred on mentors, mentees and administrators and produces the problem definition, requirements and interface prototypes. **Agile Scrum** governs *how* it is built: work is delivered in short sprints, each with a backlog, an increment that is tested, and a review with the supervisor. The two are combined because the project is both a user-facing product with uncertain needs (suited to Design Thinking) and an engineering effort with changing technical findings, such as the matching evaluation results (suited to Scrum).
>
> **3.3.1 Justification.** Alumni needs are not fully known at the start, so empathy and prototyping reduce the risk of building the wrong features. Scrum's short iterations allowed the matching engine, the mentorship workflow and later the workspace to be built, tested and adjusted in turn, with each sprint ending in a runnable, tested increment. Sprint reviews with the supervisor provided the feedback loop that the Test stage of Design Thinking calls for.

### 3.6.6 Large Language Model (RAG Architecture) (replace)

> Retrieval-augmented generation is used for the "Ask the library" feature. Published resources and announcements are embedded with the same Sentence-BERT model as the matching engine and stored in a second ChromaDB collection. A question retrieves the closest passages above a similarity floor, and a Claude model (Anthropic API, accessed through the official Python SDK) is instructed to answer only from them and to cite them; when no passage is relevant the model is not called. The language model is optional. A local open-source model was not practical on the development machine (about 7 GB of memory), and a hosted model is a paid service, so without an API key the feature runs in a retrieval-only mode that returns the closest resources as written in the library; a hosted model is a configuration option. When used, only administrator-published text is sent to the provider, so no personal data leaves the system. Answers are advisory and carry their sources, which keeps a human in the loop.
